# 昇腾赛道技术路线

项目名称：考研各专业知识库问答智能体

## 一句话定位

本项目不是普通聊天机器人，而是面向考研专业课备考的知识库问答 Agent。技术上采用“RAG 检索增强 + 多 Agent 工作流 + MindSpeed-MM/Qwen3.5 昇腾适配 + 功能/精度/性能验证”的路线，既能完成教育场景应用演示，也能对齐昇腾赛道附件要求。

## 总体架构

```text
用户问题/图片/资料
  -> 前端演示工作台
  -> Agent 路由层
       - 专业知识问答 Agent
       - 真题解析 Agent
       - 院校信息核验 Agent
       - 复习规划 Agent
  -> RAG 检索层
       - 文档解析
       - 分块清洗
       - 向量/关键词混合检索
       - 重排序
  -> 模型推理层
       - Qwen3.5 / Qwen 系列模型
       - MindSpeed-MM 适配
       - 昇腾 NPU 推理服务
  -> 结果生成层
       - 引用溯源
       - 置信度
       - 幻觉风险提示
       - 答辩可解释日志
```

## 与附件要求的对应关系

附件 1：项目创意书  
应对：创意书突出教育痛点、技术创新、昇腾适配、预期效果和可落地性。

附件 2：运行样例和赛题说明  
应对：保留官方样例运行路径，工程结构向 MindSpeed-MM 样例靠拢；我们的业务逻辑作为应用层接入模型推理服务。

附件 3：性能分析报告模板  
应对：准备性能报告，记录环境、模型、数据集、batch size、输入长度、首 token 延迟、总时延、吞吐、显存/内存占用和优化前后对比。

附件 4：COCO 数据集  
应对：如果赛题要求多模态能力或官方样例基于 COCO，本项目使用 COCO 做模型功能与精度验证；考研资料问答数据作为业务扩展集。

附件 5：功能、精度验证和性能说明  
应对：拆成三类验证：功能用例、精度日志、性能指标；每类都保留测试输入、输出、判定标准。

附件 6：精度测试日志  
应对：保留 `reports/accuracy_log.md` 或官方格式日志，记录样例编号、输入、期望输出、实际输出、评分、是否通过。

附件 7：官方代码样例  
应对：拿到 QQ 群文件后，将官方 MindSpeed-MM 样例作为 `third_party_reference` 或迁移参考；不直接混入无说明代码。

附件 8：MindSpeed MM 与 Qwen3.5 介绍视频  
应对：答辩技术说明重点讲清：MindSpeed-MM 负责多模态/大模型训练推理框架支撑，Qwen3.5 负责语言理解与生成，昇腾 NPU 负责推理加速。

## 分阶段实现计划

### 阶段 1：应用 MVP

已完成：

- 本地 Web 演示界面
- 样例知识库
- 轻量检索
- 四类 Agent 模式
- 引用溯源和风险提示

作用：答辩时展示“应用价值”和“业务闭环”。

### 阶段 2：真实知识库与评测集

需要补充：

- 考研大纲、招生简章、复试细则、真题解析
- 数据来源清单
- 20-50 条标准测试问题
- 参考答案和评分规则

作用：支撑“精度验证”和“应用可靠性”。

### 阶段 3：昇腾模型适配

目标：

- 跑通附件 2 官方样例
- 参考附件 7 MindSpeed-MM 代码样例
- 将 Qwen3.5/Qwen 模型推理封装成 HTTP 或脚本接口
- 替换当前模板化回答生成模块

接口设计：

```text
POST /api/generate
{
  "prompt": "...",
  "context": ["检索片段1", "检索片段2"],
  "mode": "qa|exam|school|plan"
}
```

### 阶段 4：功能、精度、性能验证

功能验证：

- 问答是否返回引用
- 真题解析是否包含考点、步骤、易错点
- 院校咨询是否提示年份和官方来源
- 规划 Agent 是否能按剩余时间分阶段

精度验证：

- 标准问题集命中率
- 引用命中率
- 事实一致性
- 拒答/风险提示正确率

性能验证：

- 首 token 延迟
- 单轮总响应时间
- tokens/s
- batch size 对吞吐影响
- NPU 显存占用
- 优化前后对比

## 答辩技术话术

评委问“你们用了昇腾哪里？”

回答：

> 我们把项目分成应用层和模型推理层。应用层负责考研知识库、RAG 检索和 Agent 工作流；模型推理层计划基于 MindSpeed-MM/Qwen3.5 在昇腾 NPU 上运行。昇腾部分不是简单部署，而是要按照附件要求输出功能验证、精度日志和性能分析报告，展示模型在真实教育问答场景中的推理效果和性能表现。

评委问“和普通 RAG 有什么区别？”

回答：

> 普通 RAG 只解决“找资料回答问题”。我们做的是考研场景 Agent：它会根据问题类型切换到知识问答、真题解析、院校核验或复习规划，并且每个回答都带引用、置信度和风险提示。对于招生人数、分数线、参考书这类变化信息，系统会主动提示以当年官方通知为准。

评委问“怎么证明效果？”

回答：

> 我们按附件 5 和附件 6 的思路做三类验证：功能验证看工作流是否完整；精度验证看标准问题集、引用命中率和事实一致性；性能验证看首 token 延迟、总响应时间、吞吐和资源占用，并形成性能分析报告。
